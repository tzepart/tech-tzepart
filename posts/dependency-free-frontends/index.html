Notes on Writing Dependency-Free Frontends

The dependency creep

Most frontend projects don't set out to have four hundred transitive dependencies. It happens one npm install at a time: a date formatter here, a state management library there, a UI kit because writing buttons is tedious. Each choice is individually reasonable. The sum is a lockfile nobody has fully read.

What "no framework" actually buys you

  • No build step — what you write in the file is what ships.
  • No version churn — nothing to bump when a major release deprecates an API you use.
  • Smaller attack surface — fewer transitive packages means fewer supply-chain incidents to worry about.
  • Faster cold starts — no hydration, no bundle to parse before the page is interactive.

Patterns that replace a framework

Most of what a small framework buys you — reactive updates, component boundaries, event delegation — has a plain-JS equivalent that's a few lines long once you actually need it: 

// a tiny reactive value, no framework required
function signal(initial) {
  let value = initial;
  const subscribers = new Set();
  return {
    get: () => value,
    set(next) {
      value = next;
      subscribers.forEach((fn) => fn(value));
    },
    subscribe: (fn) => subscribers.add(fn),
  };
}

For a page with a handful of interactive elements — a theme toggle, a search filter, an accordion — this is plenty. It's when the interaction graph gets tangled that a framework starts paying for itself.

Where vanilla starts to hurt

This isn't a blanket argument against frameworks. Past a certain point — deeply nested state, dozens of interdependent components, a team bigger than one person — hand-rolled reactivity turns into the exact unmaintainable mess frameworks exist to prevent. The skill is noticing when you've crossed that line, rather than assuming you're always on one side of it.

A pragmatic middle ground

My rule of thumb: reach for a framework when the page has real, branching application state — carts, wizards, dashboards. For content that's mostly static with light interactivity — like a blog — plain HTML, CSS, and a small JS file get out of the way and let the content be the product.
