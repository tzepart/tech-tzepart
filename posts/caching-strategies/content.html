The incident that changed how I think about TTLs

A pricing update went out, and for twenty-five minutes a subset of users saw the old prices. Not because the database update failed — it hadn't — but because an application-layer cache had a six-hour TTL with no invalidation hook wired up. The fix shipped correctly. The cache just hadn't heard about it yet.

The bug wasn't the cache. The bug was that nobody had written down what "fresh enough" meant for that specific piece of data.

Layer by layer: where caches live

A single request can pass through several independent caches before it ever touches a database row, and each one has different invalidation semantics:

  • Browser cache — controlled by response headers, invisible to your backend once set.
  • CDN / edge cache — shared across every user, so a bad TTL here has the widest blast radius.
  • Application cache (Redis, in-memory) — the one you have the most direct control over, and the one people forget to invalidate.
  • Database query cache — often invisible until it isn't, and rarely worth managing by hand.

Cache invalidation, the honest version

"There are only two hard things in computer science" is a cliché for a reason. In practice, the strategies that hold up are the boring ones: 

// write-through: update the cache in the same
// transaction as the write, not after it
async function updatePrice(id, price) {
  await db.prices.update(id, price);
  await cache.set(`price:${id}`, price, { ttl: 60 });
}

Time-based expiry alone is a fallback, not a strategy — it just bounds how long you'll be wrong for. Explicit invalidation on write is what actually keeps a cache honest.

Patterns that survived contact with production

  1. Short TTLs by default — a cache that expires in 60 seconds surprises no one; a six-hour TTL becomes an incident.
  2. Cache keys that include a version or hash, so a deploy can invalidate everything just by changing the key prefix.
  3. Explicit invalidation on write for anything user-facing and price- or state-sensitive.
  4. Dashboards for hit rate and staleness — a high hit rate on stale data is not a win.
