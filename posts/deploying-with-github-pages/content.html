Why static hosting

This site has no server-side logic, so it doesn't need a server. GitHub Pages hosts static files directly from a repository and fronts them with a CDN, for free, with a workflow that already ships with the actions/deploy-pages action. For a blog like this one, that's the entire hosting requirement solved in a few YAML lines.

How the workflow gets triggered

The workflow in this repo triggers on two events: a push to main, and a manual workflow_dispatch for when I want to redeploy without a new commit (useful after changing Pages settings, for example). 

on:
  push:
    branches: ["main"]
  workflow_dispatch:

Inside the deploy job

There's a single job with three steps: check out the repository, configure Pages, and upload the checked-out files as a Pages artifact. A fourth step then deploys that artifact. 

steps:
  - uses: actions/checkout@v4
  - uses: actions/configure-pages@v5
  - uses: actions/upload-pages-artifact@v3
    with:
      path: '.'
  - uses: actions/deploy-pages@v5

Because path: '.' uploads the entire repository root, there's no build step to configure — the HTML, CSS, and JS in this repo are the deployed artifact.

Caveats and gotchas

  • Pages must be switched to "GitHub Actions" as the source in repo settings, not the legacy branch-based deploy.
  • Absolute root-relative paths (/assets/...) break on project pages served from a subpath — this site uses relative paths instead.
  • The permissions block needs pages: write and id-token: write, or the deploy step fails with a cryptic 403.

A quick checklist

  1. Repository settings → Pages → Source → GitHub Actions.
  2. Workflow has contents: read, pages: write, id-token: write.
  3. All internal links and asset references are relative, not root-absolute.
  4. Push to main and watch the Actions tab.
