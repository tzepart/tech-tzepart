The parallel I didn't expect

After a few years of reviewing pull requests, I noticed the same feedback showing up whether I was reviewing code or reading a draft document: this does two things, split it, I can't tell why this exists, the name doesn't match what it does. Code review turned out to be writing feedback wearing a different outfit.

Clarity is a courtesy, not a nicety

A PR description that explains why a change exists saves every future reader — including the reviewer, and including you in six months — from having to reconstruct the reasoning from the diff alone. The same is true of a topic sentence in a paragraph. Neither is decoration; both are you doing the reader's work for them once, up front, instead of leaving it to be repeated by everyone who reads it after.

Editing yourself before anyone else has to

The best reviewers I've worked with taught me to do a self-review pass before requesting one from anyone else — read the diff as if it were someone else's, and catch the awkward naming and missing context before a reviewer has to spend their attention on it. The same read-it-back-cold pass catches more in a paragraph than any amount of staring at it while you're still writing it.

Takeaways

  • If a reviewer keeps asking "why," that's a comment or intro paragraph you forgot to write.
  • Splitting one large PR (or one sprawling paragraph) into smaller, single-purpose pieces almost always makes it easier to approve, or to read.
  • Self-review first — it's the cheapest editing pass available, and it's always available.
